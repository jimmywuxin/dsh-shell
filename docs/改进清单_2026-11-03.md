# dsh-shell 改进清单（2026-11-03）

> 来源：对照 `LibreTV-shell` 与 `opencode-shell` 三个壳的横向审查。
> 本文只列 **dsh-shell 自己要做** 的部分，另两个项目的同类项在各自仓库的文档里。
> 执行方式：Jimmy 单独指某个编号，再动手；一次一个编号、单独 commit。

## 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | 真会坏：会导致白屏、错位、功能失效，且用户无法自救 |
| **P1** | 体验/排障：能自救但成本高，或问题只能靠终端定位 |
| **P2** | 工程卫生：不影响当前使用，但会持续放大维护成本 |

## 现状基线

- 壳：`src/DshApp.swift`（638 行，NSWindow + WKWebView）
- 服务：launchd `ai.dsh.web` → `src/dsh-launch.sh`（wrapper）→ `dsh web --profile web`
- 启动：`src/launcher.sh --ensure`（kickstart → bootstrap → nohup 三级兜底）
- 共享判据：`src/dsh-lib.sh`（安装到 `~/.dsh/lib/`）
- 认证：读 `~/.dsh/.credentials.yaml` 现场 mint HMAC cookie

## P0-1 WKWebView 内容进程崩溃后永久白屏

**位置**：`src/DshApp.swift`（整个 AppDelegate，缺 delegate 方法）

**现象**：WebKit 的内容进程被系统回收（内存压力、页面 OOM）时，窗口停留在纯白/纯灰，页面无响应，⌘R 走的是 `connect()` 也未必能恢复，只能 ⌘Q 重开、丢掉全部会话状态。

**影响**：dsh 是长开常驻的（会话记忆、任务队列都在页面内存里），一次崩溃 = 一次上下文丢失。三个壳都缺这个方法，dsh 因为最常开，风险最高。

**改法**：
```swift
func webViewWebContentProcessDidTerminate(_ webView: WKWebView) {
    shellLog("web content process terminated: reloading")
    webView.reload()          // 保 cookie，等价于刷页面
}
```
- 加一个短冷却（比如 5s 内最多重载 2 次），避免页面本身必崩时无限重载刷日志。
- 重载后如果是登录态丢失（401），走 P1-3 的重铸路径。

**验收**：
1. 打开壳，`kill -9` WebKit 的 `com.apple.WebKit.WebContent` 子进程 → 窗口应在 1-2s 内自己刷新回来。
2. `~/.dsh/shell.log` 出现 `web content process terminated` 一行。

## P0-2 全屏退出后标题栏/交通灯错位

**位置**：`src/DshApp.swift:272`（`window.contentView = webView`）

**现象**：WebKit 元素全屏（`isElementFullscreenEnabled = true` 已开）进出后，窗口可能残留 `.fullSizeContentView`，标题栏变成浮在内容上的透明层，红黄绿三个按钮位置错乱，甚至掉进内容区。

**影响**：这是 WebKit 的通用坑，不是 dsh 特有。`LibreTV-shell` 已经踩过并写了完整修法（`ShellApp.swift:139-146` 容器承载 + `184-288` 几何自愈），dsh 目前一行都没接。

**改法**（两个动作，缺一不可）：
1. 改成容器承载：`let container = NSView(...)`，webView 加进 container + `autoresizingMask = [.width, .height]`，`window.contentView = container`。直接把 webView 当 contentView 时，全屏退出的 frame 账容易算错。
2. 移植 `LibreTV-shell` 的 `captureHealthyBaseline` / `titleBarIsBroken` / `scheduleTitleBarRepair` / `repairTitleBarIfNeeded` 四件套，挂到 `windowDidExitFullScreen` / `windowDidResize` / `windowDidBecomeKey`。

**注意**：dsh 有 `titlebarAppearsTransparent = true` 和动态 `window.backgroundColor`（P2 相关），自愈里「复位 styleMask」「翻转 .titled」不能把标题栏透明态冲掉 —— 修完要确认标题栏颜色仍跟随页面底色。

**验收**：
1. 页面里进一次元素全屏（若有视频/画布元素）或 ⌃⌘F 窗口全屏再退出 → 交通灯位置正常、标题栏高度 ≈28pt。
2. 拖动改窗口大小 20 次，标题栏不跑偏。
3. `~/.dsh/shell.log` 无 `repair failed: still broken`。

## P0-3 `isLocal` 只认 `127.0.0.1`，`localhost` 会被当外链甩出去

**位置**：`src/DshApp.swift:543-549`

**现象**：`dshURL` 固定 `http://127.0.0.1:3080`。若服务端任何一次 302/重定向落到 `http://localhost:3080/...`，`sameHost` 判定失败 → 交 `NSWorkspace.open` → 壳里页面直接空白，浏览器被拉起来。

**影响**：偶发、难复现、现场表现是「壳突然空了」，排障时容易误判成服务挂了。

**改法**：把 host 判定放宽到 loopback 等价类，与 `LibreTV-shell` 的 `isLocal` 对齐：
```swift
private func isLocal(_ url: URL) -> Bool {
    let hosts = ["127.0.0.1", "localhost", "::1"]
    guard let h = url.host, hosts.contains(h) else { return false }
    return (url.port ?? 80) == (dshURL.port ?? 80)
}
```
`openExternallyOrInPlace`（`:584`）里那份重复判定同步改用同一个函数。

**验收**：页面内手动 `location.href = "http://localhost:3080/"` → 壳内跳转，不弹浏览器。

## P1-1 ⌘R 语义：现在等于「重跑启动脚本，最长等 30 秒」

**位置**：`src/DshApp.swift:522`（`reloadPage` → `connect()`）

**现象**：用户想刷页面（很常见）时，⌘R 会去跑 `launcher.sh --ensure`，探测 + 等待，慢且会重铸 cookie。

**改法**：
- ⌘R → `webView.reload()`（快路径，保留 cookie 与页面会话）
- ⇧⌘R → `connect()`（慢路径，重跑 ensure + 重铸 cookie）
- 菜单里两项分开：「重新载入」/「重新连接」。

**验收**：⌘R 页面立刻刷新（<0.5s 无探测延迟）；⇧⌘R 时 `shell.log` 出现 `connect: ensuring service`。

## P1-2 缺排障入口（重启服务 / 打开日志 / 服务状态）

**位置**：`src/DshApp.swift:buildMenu()`（`:415-520`）

**现象**：服务卡住时，用户只能开终端跑 `dsh-restart`、`tail ~/.dsh/web.err.log`。壳自己完全不知道「现在服务是什么状态」。

**改法**：在「视图」菜单加三项：
- 「重启服务」→ 后台跑 `~/.local/bin/dsh-restart`（或 `launchctl kickstart -k gui/$UID/ai.dsh.web`），完成后 `connect()`
- 「打开日志」→ `NSWorkspace.open(URL(fileURLWithPath: "~/.dsh/shell.log"))`，再加「打开服务日志」指向 `web.err.log`
- 「服务状态」→ `launcher.sh --ensure` 的退出码 + HTTP 码，用 `NSAlert` 显示一行结论（就绪 / 未就绪 / cookie 失败）

**验收**：`launchctl bootout gui/$UID/ai.dsh.web` 后点「重启服务」，壳能自己恢复并加载页面，无需终端。

## P1-3 cookie 30 天过期后没有自动重铸

**位置**：`src/DshApp.swift:305-320`（只在 `connect()` 里 mint）

**现象**：cookie 有效期 30 天。过期后页面里任何请求都是 401，壳不会重铸 —— 用户看到的是空白页或「authentication required」，只有手动 ⌘R（现在）= 重连才能恢复。

**改法**：在 `decidePolicyFor navigationResponse` 里拦主框架 401，重铸一次 cookie 再 `reload()`；加 1 次上限，避免凭证真失效时死循环。同时在日志里区分「cookie 过期重铸」与「mint 失败」。

**验收**：手工把 cookie 从 `WKWebsiteDataStore` 清掉 → 下次导航自动恢复登录态，`shell.log` 出现 `auth: re-minted after 401`。

## P1-4 凭据解析失败只给一句笼统提示

**位置**：`src/DshApp.swift:125-147`（手写 YAML 扫描）、`:305-313`（失败提示）

**现象**：`browserSessionSecret()` 依赖固定缩进假设（`client-connection/browser-session:` 顶格、`secret:` 缩进 6）。dsh 某次改格式后，扫描静默返回 nil，用户只看到「读取密钥失败，请确认 DSH 启动过」——而实际 DSH 是好好跑着的。

**影响**：误导性诊断，排障会走错方向。

**改法**（低风险版，不引依赖）：
1. 解析失败时回读文件，判断三种具体原因并写进错误页：文件不存在 / 无该 block / block 在但无 `secret:` / secret 长度不是 32 字节（base64 解码后）。
2. 加一条 `shell.log` 记录：`auth: secret parse failed (reason=no-block, file=~/.dsh/.credentials.yaml)`，只记原因不记值。
3. 顺手校验文件权限：非 0600 时日志里警告一次（不阻断）。

**验收**：临时把 `.credentials.yaml` 里 `secret:` 缩进改成 4 空格 → 错误页明确说「secret 缩进不符合预期」，而不是「请确认 DSH 启动过」。

## P2-1 与另两个项目抽公共骨架

**现状**：三个壳的 `buildMenu` / `loadMessagePage` / `escapeHTML` / `shellLog` / 下载处理 / `windowShouldClose` / `showMainWindow` 几乎逐字相同，各 300-400 行重复。

**改法**（本轮不做，登记备查）：
- 抽 `ShellKit.swift`：`ShellLog`、`MessagePage`、`StandardMenu`、`DownloadHandler`、`WindowHiding`（红叉=orderOut）。
- 各项目只保留差异：URL/端口、认证策略、特有 hook（dsh 的 chrome 跟随、LibreTV 的全屏探针、opencode 的 pair 链接）。
- 放哪个仓库待定（独立 `shell-kit` 仓库 or 三处 vendored 副本 + 同步脚本）。**必须先定分发方式再动手**，否则三份副本变四份。

**验收**：三处 `swiftc -typecheck` 通过，且体积/行为无变化。

## P2-2 端口/URL 三个来源

**位置**：`src/DshApp.swift:20`（`dshURL`）、`src/dsh-lib.sh`（`URL`）、`src/ai.dsh.web.plist`（端口隐含在 node argv）

**问题**：换端口要同步改三处，漏一处就是「壳连不上、服务好好跑着」。

**改法**：`Info.plist` 加 `DshServiceURL`，壳从 `Bundle.main.infoDictionary` 读；脚本从同一份 `dsh-lib.sh` 常量派生；plist 渲染时同源。

## P2-3 ad-hoc 签名，换机/分发会被 Gatekeeper 拦

**位置**：`build.sh:171-172`（`codesign --sign -`）

**说明**：本机自用没问题。一旦拷给别人（或将来重装系统后从备份恢复），首次打开会被拦，需要手动 `xattr -dr com.apple.quarantine`。

**改法（择一）**：① 有开发者账号 → Developer ID 签名 + notarize；② 没有 → README 里写明放行步骤，别让人以为包坏了。

## 执行建议顺序

```
P0-1 → P0-2 → P0-3 → P1-1 → P1-2 → P1-3 → P1-4 → （P2 另行评估）
```

理由：前三条是「会坏且救不回」，P1-1/P1-2 直接降低日常排障成本，P1-3/P1-4 是边角但低成本。P2-1 牵扯仓库结构，单独决策。

## 改动约束（每条都适用）

1. **改完必须重跑 `bash build.sh`**：`launcher.sh` / `dsh-lib.sh` / `dsh-launch.sh` 会被安装到 `~/.dsh/lib/` 与 `.app` 内，只改 `src/` 不重建 = 跑的还是旧脚本。这是本项目最容易踩的坑。
2. `dsh-lib.sh` 改动后必须跑 `bash src/dsh-lib.sh` 自检（内含 5 条断言）。
3. 破坏性操作（`bootout`、杀进程、覆盖 `.app`）先提案再执行；`.app` 旧版进废纸篓。
4. 活服务文件只 `cp` 不 `mv`。
5. 改完真机验收，不接受「编译通过即完成」。
6. 版本号：纯修复按 patch 累积，小改动不单独发版。
